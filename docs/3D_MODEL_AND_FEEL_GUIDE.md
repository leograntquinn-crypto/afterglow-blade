## ① 跑步"手和大腿粘连"的诊断与修法

### 1.1 先把现象定义清楚（防止各说各话）

Quinn 看到的"粘连"在工程上可能是四种完全不同的东西，诊断第一步是分流：

| 类型 | 特征 | 归属 |
|---|---|---|
| **A. 权重串扰（skinning bleed）** | 动作摆动时手/前臂网格被大腿骨"拽着走"，或大腿网格跟着手骨变形，出现网格拉伸、尖刺、布料一样的拉扯感 | 蒙皮权重（Blender） |
| **B. 姿势贴碰（pose contact）** | 网格本身不变形，但 run 循环中手摆轨迹离大腿太近（< 2–3cm），视觉上贴住/穿插 | 动画姿势（run 片段） |
| **C. 附件骨链干扰** | 衣摆、袖口、马尾、腰布骨链在运行时弹簧或权重参与下贴到腿上 | 附件权重/弹簧骨配置 |
| **D. 引擎侧变形** | Blender 里正常，进 Godot 才变形（导入缩放、骨架 rest pose、动画采样差异） | 导入配置（Godot） |

> 你可以先斩钉截铁排除 D 的嫌疑：`player3d.gd` 里用于归一化的 `normalized.scale` 是**统一比例**，不存在非均匀缩放拉伸网格；弹簧骨当前 `spring_count = 0`（S1 骨架没有发/腰布链），**所以 C 在当前版本也不会发生**。当前最可疑的是 A 和 B——这正是 Tripo 自动绑骨 + 快速重涂最容易翻车的两处。

### 1.2 定位流程（按顺序做，每步都有判定标准）

**Step 0 — 取证（30 分钟）**
1. 打开的是 **Blender 源母版**（重涂骨架那一份），不是 `feisun_s1.glb`。
2. 播放 run 片段（先测出循环长度：Run 周期 T 秒、采样帧数），以 60fps 逐帧看，录屏。
3. 记录：粘连最早出现的帧号、左/右手哪一侧、画面是"拉伸"（→ A）还是"贴近"（→ B）。

**Step 1 — 三分离实验（10 分钟，一次定乾坤）**

| 实验 | 操作 | 判定 |
|---|---|---|
| E1：隐藏附件 | 隐藏衣摆/袖/马尾/武器，只留身体网格，播 run | 粘连仍在 → A 或 B；消失 → C（附件权重，去查附件 Data Transfer 的左右分区） |
| E2：关物理/修改器 | 关掉所有 Skeleton 修改器、弹簧、保留动画 | 粘连仍在 → 姿势或权重问题（继续 Step 2） |
| E3：单骨抖动 | 摆一个静止的压力姿势（抱胸/跨步），单独旋转 UpperLeg 与 ForeArm | 旋转大腿时手部网格或前臂网格有任何位移 → **A 类权重串扰，且已锁定到该骨** |

**Step 2 — 权重普查（精确定位"哪片权重"）**
1. Weight Paint 模式，选 `thigh.L/R`（大腿骨）：看影响是否越过髋部延伸到前臂/手部顶点。**判定线：手部区域顶点上大腿骨权重必须恰好为 0。**
2. 反向选 `hand.L/R` / `forearm.L/R`：看大腿区域顶点是否被拾取。**判定线：大腿顶点上手臂骨权重 = 0。**
3. 用 "Select All by Trait → Vertex Group" 或导出 `qa/weight_audit.csv`（每顶点影响骨列表）扫全模型：
   - 每点影响骨 ≤ 4；
   - 微权重 < 0.01 全部清零；
   - 权重总和 = 1.0 ± 0.01（normalize）；
   - **左右分区检查**：无任何顶点同时持有 `.L` 与 `.R` 肢体骨的高权重（> 0.1）——Tripo 自动绑骨和 Data Transfer 最常见的串扰就是左右不分/远近不分。
4. 把"旋转 thigh 0.6 rad 时手部探针位移"作为定量指纹：**正常应 < 1mm；如果在跑，它就是串扰的铁证**（这就是"三验"里的②杠杆扫描，见 ③.9）。

**Step 3 — 姿势检查（若权重干净）**
1. 输出 run 全周期"手网格最低点到大腿网格最近点"距离曲线（Blender 里用 bmesh 最短距离或 MeasureIt 逐帧量；Muse 可写 `bpy` 脚本批量出 CSV）。
2. 判定线：1.7m 体型下，**手/前臂与大腿最小间隙应 ≥ 2cm**；低于 2cm 即视觉粘连，低于 0 即穿模。
3. 若贴碰 → 修姿势（见 1.3 的 B 类修法）。

**Step 4 — 引擎侧排除（只有 Blender 干净才走到这步）**
1. 对比同一帧在 Blender 与 Godot 的骨骼姿态（`Skeleton3D` 画骨显示）——不一致才查导入设置；
2. 检查 GLB 导入是否做了顶点量化（带骨骼角色**禁止**顶点量化，否则极瘦部位像手会变形）、是否正确保留 custom bone poses；
3. 头顶高度误差 < 1mm（打包前后对比，沿用的管线纪律）。

### 1.3 修法（按归类执行，全部在 Blender 源母版里做，重新走管线第 6–8 步，不在 Godot 里硬改）

| 归类 | 修法 |
|---|---|
| **A. 权重串扰** | ① 手/前臂/大腿三区手工重涂：区域顶点权重归位到本区骨，交界（腕、肘、髋）用 2–3 圈渐变过渡；② 左右镜像用 `Weights → Mirror` 保证对称；③ 清理微权重、limit 4、normalize；④ **重跑 Step 2 全部判定线，全绿才算修完**；⑤ 如根因是 Tripo 自动绑骨质量差，按管线纪律"平台绑骨只作初稿"，以标准人体/干净骨架为 donor 做 Data Transfer（Nearest Face Interpolated）+ 左右分区 mask，再手工收边。 |
| **B. 姿势贴碰** | 改 run 片段关键帧，不动战斗片段：① 手臂摆动外展 3–5cm（避免直臂贴身内旋），肘部保持 15–20° 放松弯曲；② 大腿抬升相位与手臂对侧摆齐（对侧手垂下时大腿在最高点，本身是最贴腿的瞬间——重点修这一帧）；③ 必要时光顺 Hips 侧倾 2–3°。改完重出 1.2 Step 3 的距离曲线。 |
| **C. 附件** | 修附件权重的左右分区与 distance 阈值；衣摆下缘权重衰减到腿骨为 0；弹簧骨链（新模型）按 ③.7 命名与参数，验收含"全套动作穿透深度 < 1cm"。 |
| **D. 引擎侧** | 关顶点量化、重导入、对齐骨架 rest pose；此项若判实，写进 `qa/` 报告给 Fable 改导入钩子。 |

### 1.4 验收标准（这类"很抽象"的问题如何被拦住)

把主观感受拆成三条可自动化的硬指标，缺一不算交付：

1. **权重普查表**（`qa/weight_audit.csv`）：手部顶点上腿骨权重 = 0、腿部顶点上臂骨权重 = 0；每点 ≤ 4 影响；总和 1.0 ± 0.01；无左右混权 > 0.1。
2. **杠杆扫描表**（`qa/lever_scan.csv`）：逐骨旋转 0.6 rad，各探针（双手、双脚、头顶、马尾尖、腰带尖）位移表——旋转上肢骨时下肢探针位移 < 1mm，反之亦然。
3. **全周期距离曲线 + 截图条带**（`qa/run_clearance.csv` + `qa/run_strip.png`）：run 全周期逐帧手↔大腿最小距离 **≥ 2cm**（or 允许贴但不穿——以视觉评审为准，但必须有曲线证据）；30/60/144 FPS 三档各跑一遍，结果一致；游戏镜头（45°/16m/FOV38）下录屏复核。
4. 回归：`--verify` 仍 PASS（12/12/16）、`--demo --god` 仍 PLAY VICTORY；三连斩/受击/倒地全部片段过同一距离检查。

> 这套东西的价值：以后每次换模型/换权重，Muse 用同一套脚本重跑三张表对比，就能在 Quinn 看到之前拦住同类问题。UE/Unity 也不会自带这些表——所谓"UE 行走手感好"是人家有 Motion Matching 和大量人工打磨的动画资产，不是引擎魔法，见 ②.4。

## ② 行走手感：步频/车速修法 + 引擎问题判断

### 2.1 现状事实（代码已核对）

| 项 | 现状 | 出处 |
|---|---|---|
| 代码移速 | `MOVE_SPEED := 4.2` m/s（走跑同速，按住方向即 run） | `scripts/player3d.gd:3` |
| run 片段自然速度 | Tripo 预设片段，约 **2.3m/s**（Quinn/Muse 实测口径） | 路线图第 9 项 |
| 根位移处理 | `_pin_root()` 把**全部片段** Hips 水平位移钉在首帧，只留纵向起伏；位移完全由胶囊控制器驱动 | `scripts/player3d.gd:106` |
| 结果 | 身体 4.2m/s、足底动画速度 2.3m/s → **滑步率约 (4.2−2.3)/4.2 ≈ 45%**，脚在支撑相往前后扫，这就是"不丝滑"的主因 | 推算 |

补充两个隐性手感问题（一并列入修法）：
- 速度是**瞬时赋值**（`velocity.x/z = direction * MOVE_SPEED`），无起步/停止加速度，起步即满速、松手即停，视觉上"钉"在地上挪。建议加速度 25–30 m/s²（约 0.14–0.17s 到满速），run→idle 用 0.15s 降速。
- 转向用 `TURN_SPEED = 10 rad/s` 插值，尚可，但起步/急转时可加 0.05–0.1s 的短暂减速（可选，Quinn 实机定夺）。

### 2.2 定量标准（先量后修）

- 测当前 clip：周期时长 T、每周期根位移 D（若已被钉掉，用 Tripo 原始未处理导出测），自然速度 = D/T。
- 目标：**支撑相脚底相对地面滑移 < 5%**（即动画足速与胶囊速度差 < 0.21 m/s）；急停滑行距离 < 0.2m；30/60/144 FPS 三档手感一致。

### 2.3 三条修法路线（推荐 A，C 为可选升级，B 只作临时补丁）

| 路线 | 做法 | 优点 | 缺点/风险 | 适用 |
|---|---|---|---|---|
| **A. 动画匹配速度（推荐）** | 在 Blender 重制 run 片段：步幅 +35–45%、步频 +25–30%，使片段自然速度 = 4.2 ± 0.2 m/s（参考：步态周期 0.62–0.72s、单步 1.26–1.51m，视觉复核后冻结）。代码继续 `_pin_root` + 胶囊驱动，一行代码不改 | 最稳：位移、碰撞、磁吸、击退、跳跃全部维持现状；`--verify` 天然安全；滑步从根上消失 | 需要一版新 run 动画（可与其他动画一起在新模型里做） | **首选** |
| **B. 代码侧同步播放速率（临时补丁）** | `_play_anim("run", MOVE_SPEED / 2.3 ≈ 1.83)`，让足速与车速对齐 | 一天内见效，零资产 | 步频 1.83× 显得忙乱急促，整体节奏不高级；run 片段音画感变调 | 仅当 Quinn 需要短期缓解；报告里必须标注"临时" |
| **C. 根运动（root motion）** | 新骨架提供独立 `Root` 骨（脚底中心、朝前 −Y Blender / −Z Godot），run 片段保留干净的水平根位移；`AnimationPlayer` 开 root motion，移动用根位移驱动，转向/战斗冲刺（磁吸）、击退、跳跃仍代码驱动；**攻击片段保持钉根不变** | 脚速与位移数学上永远一致，最高级手感；也是未来 Motion Matching 式管线的地基 | 需要资产侧提供干净根位移（Tripo 预设动作通常无）；与磁吸/击退的混合逻辑要设计；是"升级"不是"修理" | 可选升级项，Muse+Quinn 决定是否在本次换新一并做 |

**建议**：本次随新主角模型直接交付 **A 方案 run（4.2m/s 匹配版）**；如果 Muse 在新模型上能顺手产出干净根位移片段，则把 C 作为第二阶段评估项（不在本次上线范围内）。B 只允许作为过渡补丁。

### 2.4 "是不是 Godot 引擎不行？要不要换 UE/Unity？"——判断与理由

**结论：不换引擎。换引擎解决不了这两个问题，反而会引入更大的问题。**

1. **粘连是资产问题，与引擎无关。** 权重串扰/姿势贴碰在 Blender 里就能复现（①.2 的 E1–E3 实验不经过任何引擎）。同一份坏权重导入 UE5 或 Unity 会一样粘连——他们并不自带"防粘连"魔法，靠的是人工重涂 + 验收表（我们 ①.4 就是在补这张表）。
2. **滑步是方案问题，与引擎无关。** 我们的架构是"钉根 + 代码移速"。UE 里如果把人钉在原地、代码赋 4.2m/s、动画 2.3m/s，滑得一模一样。UE 行走"手感好"的真实原因是 **Motion Matching + 几分钟级体量的高质量动捕/手工动画资产**——那是加分项，不是引擎的免费午餐；Godot 侧换成"动画匹配速度（A 方案）"后，视觉一致度可以达到同样的水平。
3. **本方案所需能力 Godot 4.7.2 全部具备且已在用**：根运动（C 方案随时可开）、`SpringBoneSimulator3D`（弹簧骨）、体积雾/SSAO/泛光（场景 v5）、`AnimationTree` 状态机、无头自动验收（`--verify` 系列，CI 可跑——UE/Unity 侧的无头验收工程量大得多）。项目的数据层、存档、帧战斗系统（12/12/16 红线）也都已经在 Godot 里验证过一轮。
4. **换引擎的真实成本**：战斗帧数据系统（22 帧/判定 6/取消 10/防连晕）全部重写并重验；GDScript→C#/蓝图重写；Muse 的资产管线（Blender 交付中间件）可复用，但导入/材质/后处理全部重审；Steam 集成（GodotSteam）、存档、UI 重来；**周期内 Quinn 拿不到任何改进，还丢了已验证的手感**。收益近乎为零。
5. **什么情况下才值得再讨论换引擎**（触发信号，现在一个都不满足）：需求升级到大规模人群 Motion Matching、Nanite 级场景密度、商用布料/毛发全局模拟；或者做了性能剖析后，证明目标设备上 Godot Forward+ 确实达不到帧率红线（目前 P1–P6 未实测完，谈不上证据）。真到那天，先出带数字的性能对比报告再决策。

**给 Muse 的执行口径**：手感问题按 2.3 的 A 路线修；引擎讨论冻结，除非出现 2.4 第 5 条的硬证据。

### 2.5 手感验收标准

1. 支撑相足底滑移 < 5%（逐帧测脚骨水平速度 vs 胶囊速度，出 `qa/run_footslip.csv`）。
2. run 自然速度 4.2 ± 0.2 m/s；急停滑行 < 0.2m；起步 0→满速 ≤ 0.2s 且无"瞬移感"。
3. 30/60/144 FPS 三档录屏一致；游戏镜头下 10 秒 run 循环无视觉滑步、无粘连（联动 ①.4）。
4. `--verify` PASS（12/12/16 不动）、`--demo --god` PLAY VICTORY、demo 用时与基线偏差 ≤ 10%。
5. **Quinn 实机试玩签收**——手感类结论最终以 Quinn 的判断为准，我们不拿数值替代他。

## ③ Tripo / Hyper3D Rodin 资产制作指导与规格

### 3.0 平台分工与纪律（沿用已定版管线）

| 平台 | 定位 | 关键事实（既往教训入册） |
|---|---|---|
| **Hyper3D / Rodin** | 主力"生"：主角身份母版、高模形体，身份还原最强 | 材质选 **4K**（选过 8K 后选项丢失的教训）；生成/确认后**立即下载**并解压校验，云端历史不算交付；绑骨只作初稿 |
| **Tripo AI（国际站专业版）** | 加工车间 + 备选生成：重拓扑（Smart Mesh，可设面数）、智能 UV、自动绑骨（7 类生物）、动作库与重定向、分割/补面、PBR 重贴图 | **Studio 内不能改骨骼与权重**；肩部变形是官方自认常见问题；AI 头发是静态的；重拓扑会丢 UV 需重贴图。这些全部在 Blender 里收尾 |
| **Blender** | 唯一装配/验收权威 | 平台产出只进 raw 区，永不直接覆盖已验收母版 |

通用纪律：
- 每个资产先开 task 台账（task ID、参数、费用、下载 hash），一次不达验收不连环抽卡——**两轮还不行就改输入图或转手工**。

### 3.1 参考图准备规范（所有生成的共同前置，不合格不进入生成）

1. **三视图冻结**：正交前/侧/背各一张，**同一姿势（A-pose 30–45°、双腿分开、手臂离身）**、同一比例尺（1.7m 身高标记）、中性平光、无烘焙阴影、透明或纯色背景、长边 ≥ 1024px。背面**不许让生成器猜**，必须出图。
2. **风格页**：色板（HEX）、材质块（金属/布料/皮革/皮的反射倾向）、脸部与身份标记（脸型、发型、马尾长度、剪影特征）单独出特写图，且**衣服输入图里去掉脸**（防身份漂移）。
3. **剪影先行**：先看游戏镜头角度（45° 俯角）下的剪影是否成立，再看特写。
4. 道具/硬表面件（鸟居、立石等）：正/侧两张 + 关键尺度标注（米）。

### 3.3 主角新模型（整体换新，Quinn 已拍板）

**目标**：替换 `feisun_s1.glb`（300k 面 / 58 骨 / 缺 attack1 / 缺发与腰布链），新模型一次带齐：run 4.2m/s 匹配版动画、attack1、马尾与腰布骨链。文件名建议 `feisun_s2.glb`，旧的保留为 fallback（`player3d.gd` 的 `model_path` 改指向由 Fable 一侧接工单做，Muse 不动代码）。

**流程（按管线十二步执行）**：

1. **设定冻结**：三视图 + 脸特写 + 身形比例表（头身比、肩宽、腿长按 S1 身份锁定）；色板冻结。
2. **生成**：Rodin 出身份母版与高模（4K 材质，立即下载校验）；Tripo 同图对照 2–4 个候选；按"游戏镜头剪影 → 特写"顺序评。
3. **拓扑**：可变形游戏网格（身体+主衣装）建议 **80k–150k 三角面**，武器配件单独 ≤ 20k；肩肘髋膝有可控环线；无内壳、反法线；**干净中模 + 高模烘焙 4K 法线/AO**（沿用"不要低模"的质量口径）。高模原档完整留档 `source/`。
4. **UV/材质**：脸/身 4K、配件 2K；去烘焙光照；粗糙度范围统一；贴图密度一致（头部优先）。
5. **绑定**：转进项目骨架规范（3.7 全表），**加装马尾链（HairRoot/HairTip 与 PonytailRoot/PonytailTip）与腰布链（WaistClothL/R_01–03、WaistL/R_01–03）**，加 `Root` 骨（脚底中心、前向 −Y）为 C 方案预备；权重不接受平台自动结果直接入库。
6. **权重**：标准流程 + **本工单新增的防粘连检查表**（①.2 的判定线全部入验收）：左右分区、微权重、limit 4、normalize、杠杆扫描、手腿间距曲线。
7. **动画**：现有 12 段全部重定向到新骨架（骨名映射表由 Muse 出，存 `qa/retarget_map.csv`）；**run 按 ②.3 A 路线重制（自然速度 4.2m/s）**；**attack1 新做**（见 3.4）；其余片段保持原节拍（攻击仍是 22 帧/判定 6/取消 10，帧数据红线不动）。
8. **配件**：武器、发带、饰品按挂点骨 `socket_weapon.R`、`socket_back`、`socket_head` 适配。
9. **验收**：3.9 全表 + `verify_spring_bone.gd` 从 BLOCKED 翻绿 + `verify_attack1.gd` 检出 attack1 + 三验报告入 `qa/`。
10. **发布**：`source/master/game/qa/` 目录结构完整，新机器可复现装配。

### 3.4 attack1（第一段劈砍动画）

**注意：这不是模型资产，是动画资产，Tripo 的文生动作只能做 previs 草稿，不能做交付。**

- **参考**：挥砍参考视频或逐帧故事板（右肩起手 → 蓄势 → 挥出 → 过冲 → 收回），至少 8 张关键帧草图；武器轨迹弧线图（平面投影）。
- **规格（红线，不可动）**：总长 22 帧 @60Hz（30fps 母版烘焙成 60Hz 采样可）、**判定帧 6–7**、第 10 帧起可衔接下一段、根位移水平钉死（沿用 `_pin_root` 口径，Hips 只留纵向起伏）、起止姿态与 idle/attack2 链在 0.12s 淡入淡出内可衔接。
- **制作**：在新骨架上手 K（Blender），Dope Sheet 关键帧：0–2 起手 / 3–5 蓄势停顿（约 0.05–0.08s）/ 5–8 挥出（四次方缓出，刃尖在此段扫完整弧）/ 8–11 过冲 / 11–22 收回。手在挥砍全弧中**离大腿 ≥ 2cm**（联动 ① 的检查表，新动作不许带新粘连）。
- **验收**：`--verify` PASS 且接触帧落点正确；`verify_attack1.gd` 检出片段；游戏镜头录屏评审挥砍可读性；三连斩衔接（第 10 帧输入缓冲接第二段）无跳帧。

### 3.5 地面敌人真模型（腐骨兵等）

### 3.7 骨架与骨链命名强制表（马尾/腰布单独强调）

**核心骨**（语义层级与 Blender/Z 上、朝 −Y、脚底原点、米制的管线规范一致）：

```
root（脚底中心，供根运动）
└─ pelvis
   ├─ spine_01 → spine_02 → chest → neck → head
   │            │
   │            ├─ clavicle.L/R → upper_arm.L/R → forearm.L/R → hand.L/R（五指各 3 段可选，主角必须）
   │            ├─ socket_weapon.R / socket_weapon.L / socket_back / socket_head
   │            └─ （弹簧骨挂载点：HairRoot 父到 head 或 head 下级）
   ├─ thigh.L/R → shin.L/R → foot.L/R → toe.L/R
   └─ （腰布链父到 pelvis）
```

**弹簧骨链命名（必须逐字一致——`scripts/spring_bone_runtime.gd` 里只有这五条链的探测代码，名字错一个字母就探测不到）：**

| 链 | 起止骨（探测器认的首尾名） | 中间段要求 |
|---|---|---|
| 主发束 | `HairRoot` → `HairTip` | 中间可任意，但必须构成无分支链，段数 ≤ 6 |
| 侧发链 | `Hair_01` → `Hair_05` | `Hair_01..Hair_05` 连续编号（若做双马尾：`Hair_L_01..` 与 `Hair_R_01..`，同时保留一组平名链，或由 Muse 提映射表由 Fable 改探测器常量） |
| **马尾** | `PonytailRoot` → `PonytailTip` | 马尾必须做成 **3–6 段**骨链（推荐 5 段：`Ponytail_01..05`），根段 stiff 高（约 1.5×）近似锁死，尖段软；起点挂头骨后下方 |
| 左腰布 | `WaistClothL_01` → `WaistClothL_03` | 3 段起 |
| 右腰布 | `WaistClothR_01` → `WaistClothR_03` | 3 段 |
| 左腰侧饰带 | `WaistL_01` → `WaistL_03` | 3 段 |
| 右腰侧饰带 | `WaistR_01` → `WaistR_03` | 3 段 |

**弹簧骨碰撞体**：在骨架挂 `SpringBoneCollisionSphere3D` / 胶囊：头部（半径 ≈ 0.11m）、胸部（胶囊 0.13m）、骨盆（0.13m）、大腿左右（0.08m）、上臂（可选 0.06m）。半径按 1.7m 体型给，按穿透验收微调。

**骨骼技术要求**：每骨 scale = 1、无剪切；roll 与现有 S1 骨架一致（retarget 误差最小化）；rest pose A-pose 30–45°；骨名大小写逐字对照本表（`.L/.R` 后缀保留管线习惯）。改任何骨名的唯一例外是"Muse 提映射表 → Fable 改 `spring_bone_runtime.gd` 常量"的工单流程，不得静默改名。

### 3.8 导出与导入要点

1. GLB（glTF 2.0），内嵌贴图（或同目录贴图），米制，**应用全部变换**。
2. 动画：30fps 母版、60Hz 采样兼容；循环片段 [0,T) 不含重复尾帧；片段名精确：`idle/walk/run/attack1/attack2/hit/hit2/death/jump/jump_down/cast/dive/relax`。
3. 导入 Godot 4.7.2：**禁用顶点量化**（带骨骼角色）；检查骨架 rest pose 与动画采样无偏移；头顶高度打包前后误差 < 1mm（`feisun_s1` 当年即按此纪律验收）。
4. 贴图导入：albedo sRGB、normal/ORM 线性；法线贴图压缩格式选法线专用，不混用 albedo 压缩导致色带。
5. 命名/目录：`art/models/<name>.glb` + `qa/<name>/` 三验报告与地图；旧资产不得覆盖删除（fallback 保留）。

### 3.9 统一验收清单（每个资产通用，缺一不算交付）

## G-3 掉落与旧系统

- **掉落**（`randomDrop(L, opts)` 签名不变）：
  - 先按稀有度权重抽稀有度，再按关卡的系列权重抽系列（系列表里的主要掉落关卡权重 ×3），再抽款式（槽位权重沿用旧比例，新槽位均分剩下的份额），最后在这一格的保底件和变体里随机抽一个。
  - **传说**只从这几个来源掉：
    - 首领套装件：从对应首领掉；
    - 独立传说：从试炼和难度 ≥ 1 的通关奖励掉；
    - 保底计数：`save.legendPity`，同一来源连续 8 次没出传说，第 9 次必出。
  - **翅膀 / 光幕**：第一件从第 2 关首领起才会掉（设计稿第一节第 3 条）。
- **强化 / 重铸 / 传承 / 出售**：
  - 公式里的 `it.rar` 改查一张「费用档」表：普通 0、精良 1、稀有 2、史诗 2.5、传说 3，这样旧装备的价格不变；
  - 翅膀 / 光幕不能强化、重铸、传承，按钮置灰并说明原因；
  - 两个饰品槽之间可以互相传承。
- **刻印、铭刻**：照旧。

## G-4 比较口径、标定、`REF_POWER`（核心，严格按设计稿第九节）

新文件 `src/gear/compare.js`，导出 `compareItem(save, cand)`，返回：

```js
{ slot, against,                 // 和哪一件比（饰品取两个槽里较弱的那件，可传参指定）
  enhAs,                         // 折算用的强化等级 = 身上那件的强化等级（没穿 = 0）
  parts: { base, effect, buff }, // 三段各自的战力变化百分比，逐段累计
  total,                         // 三段合计（%）
  verdict,                       // 'much' | 'better' | 'same' | 'worse' | 'muchWorse' | 'playstyle'
  reasons: [] }                  // 物品等级差、套装件数变化、条件型效果……（文字 id + 参数）
```

- **同强化折算**：两件都按 `enhAs` 计算基础属性（复制实例、改 `enh`，**不改原实例**）。原实例的强化等级不进任何一段。
- **战力变化**：用 `computeStats` 算「身上全套」和「换进这一件的全套」，再过 `power()`。三段分别是：
  - **基础**：只换基础属性；
  - **效果**：再加随机词条和刻印；
  - **buff**：再加状态词条、套装、搭配，按「战力当量表」折算。
- **战力当量表**（`src/gear/rating.js`，数据）：
  - 每条刻印一个值；每档状态词条一个值；套装 2 / 4 件、搭配效果各一个值。
  - 本模块里状态 / 套装 / 搭配的值先填 0，留着由状态模块补；刻印按我给的初值：每条 = `power` 的 3%，`desperate` / `pristine` 这种窄条件的 2%。
  - `power()` 也读这张表（首领动态难度用的同一张）。
- **结论分级**（设计稿第九节第 3 条）：≥ +5% 明显更强，+1%～+5% 略强，±1% 相当，往下对称。基础 + 效果的方向和 buff 的方向相反、而且决定胜负的是条件型效果时，结论为 `playstyle`（◆，不给 ▲）。
- **删掉 `itemScore`**：背包 ▲、整理排序、拾取「最佳」、详情页对比全部改用 `compareItem`。**任何推荐都不许读含强化差异的总战力。**
- **标定**：词条质量系数和区间收窄已经在 G-2 里，这里用测试守住（G-6）。
- **`REF_POWER` 重算**：
  - 新脚本 `tools/refpower.js`：按第 12 项的同一方法（每级 200 套同级精良装备，力量 / 体质各一半属性点），用新槽位算；
  - 翅膀 / 光幕从 4 级起计入（第 2 关首领起才掉）；
  - 结果写回 `src/boss_scale.js` 的 `REF_POWER`，脚本输出和表逐项一致。

## G-6 确定性测试 `tests/gearmodeltest.js`

加进 `tests/run_all.js`，最后一行 `GEARMODELTEST ok` / `GEARMODELTEST FAIL n`。要测：

1. **目录**：
   - 保底 308 + 传说 36 件都在，每个「系列 × 款式 × 档」格子都有；
   - id 唯一、只含小写字母数字下划线；
   - 每件的字段齐全，`classReq === null`、`pvp === false`。
2. **翅膀 / 光幕**：抽 200 件（各稀有度），`itemStats` 全部恰好是 `{ atk: 10 }`；不计套装件数；不能强化 / 重铸 / 传承。
3. **预算**：在物品等级 1、10、20、30，同稀有度下，非武器七个槽的基础属性合计 = 旧头盔 + 护甲 + 戒指（容差 ±1）。
4. **迁移**：用 `tests/fixtures/save_v1_{early,mid,late}.json` 这 3 份旧存档样本（已入库，用旧代码按固定随机种子生成：新手；中期四件精良 / 稀有带强化、刻印、重铸、锁定，背包 20 件；后期 5 件旧传说、强化 7～10、背包 40 件），检查：
   - 件数不变；
   - 每件 `itemStats` 每一项 ≥ 迁移前；
   - 旧传说变成 `rar 4`；
   - 迁移两次结果相同（幂等）；
   - 加载时自动迁移。
5. **标定**（模拟，每组 10 000 对，用固定随机种子）：同物品等级、同强化、不算套装 / 搭配时，低一档赢高一档 ≤ 5%，低两档 ≤ 1%（按 `compareItem` 的结论计）。
6. **比较口径**：
   - 身上一件「精良 +8」、背包一件同级「史诗 +0」：结论必须按 +8 折算，史诗更强；
   - 反过来「史诗 +8」对「精良 +0」：精良不能被判更强；
   - 原实例的 `enh` 在比较后不变。
7. **推荐不读总战力**：把 `power()` 临时改成含强化的错误版本，`compareItem` 的结论不变。
8. **`REF_POWER`**：`tools/refpower.js` 的输出和 `boss_scale.js` 的表逐项一致。
9. **页面无报错**，最后一行汇总。
